# SND: диагностическая сборка

Основа: актуальная `origin/main`, commit `d645fe762c90ee97cef05a0541394967f4b922f0`
(проверено `git pull --ff-only origin main` 27 октября 2026).
NLua 1.7.9 / KeraLua 1.4.9 / Dalamud API 15.

## Загрузка

После сборки комплект DLL находится в `SomethingNeedDoing/bin/Debug/`.
В Dalamud Developer Plugin Locations добавьте путь к
`SomethingNeedDoing.dll` из этой папки и используйте эту dev-сборку вместо обычного SND.
Для проверки после смены DC полностью перезапустите игру: прежние Lua-среды
могут содержать ссылки, полученные до загрузки диагностики.

## Журнал

Пишется автоматически, независимо от уровня журнала Dalamud:

```text
%APPDATA%\XIVLauncher\pluginConfigs\SomethingNeedDoing\diagnostics\lua-crash.log
```

При достижении 8 МиБ файл перемещается в `.1`, предыдущий `.1` — в `.2`.
Всего сохраняются три файла. Строки сразу сбрасываются из буфера .NET в файл,
чтобы пережить падение процесса. Это не гарантия сохранности при сбое питания.
После краша сохраните все три файла вместе с соответствующим
`dalamud_appcrash_*.log` / `.dmp`.

Каждая запись содержит время с часовым поясом, PID, уникальный номер запуска
макроса (`run`), имя и ID макроса, адрес Lua-среды, номер шага и ID потока.

- `SETUP`: триггер запуска, SHA-256 текста без метаданных.
- `BEGIN` / `END`: загрузка, зависимости, возобновление корутины, триггер,
  cleanup и Dispose. Незакрытая пара помогает определить незавершённую операцию;
  учитывайте следующие записи `ERROR` и другие вложенные операции.
- `LIFECYCLE`: вход/выход, зона и флаги загрузки; перечисляет существующие Lua-среды.
- `TRIGGER-SKIPPED`: макрос уже отслеживается, его состояние и пропущенный триггер.
- `OBJECT-FIRST-SEEN`: внутренний номер NLua и управляемая идентичность сырого
  игрового объекта / EntityWrapper, источник и последняя исполнявшаяся строка.
- `GC-Call` / `GC-Return`: начало и завершение исходного сборщика NLua для
  наблюдавшихся игровых типов. `GC-Call` записывается **до** исходного
  `Dictionary.Remove` / `GetHashCode`; содержит строку первого наблюдения.

Если стек нового дампа снова содержит `NLua.CollectObject → GameObject.GetHashCode`,
найдите последнюю `GC-Call` без соответствующей `GC-Return` с теми же `run` и
`object`. Она определяет макрос и CLR-объект, на очистке которого произошёл сбой.
`last=` показывает последнюю Lua-строку, а не обязательно место получения объекта;
`firstSeen=` помогает найти место получения. Наблюдение идёт на границах строк и
вызовов: это ближайшая наблюдавшаяся строка, не полный трассировщик CLR-доступов.
Если объект упал при первоначальной передаче в NLua, до первого наблюдения, записи
`GC-Call` может не быть — смотрите незавершённый `BEGIN` и аварийный стек.

Для источника `snd/<id>/entrypoint` из Lua-номера строки нужно вычесть **4**,
чтобы получить номер строки в тексте макроса **без метаданных**.
Для файлов зависимостей смещение отсутствует.

## Ограничения

Это диагностика, не исправление исходного краша. Она не меняет хеширование NLua
и не отключает GC. Она добавляет строковые
hooks и оборачивает `__gc` только на наблюдавшихся игровых CLR-типах, проверяя,
что исходный обработчик соответствует `NLua.MetaFunctions.GcFunction`.
Исходный обработчик вызывается с теми же аргументами и результатом.
Хуки Lua не работают внутри самого `__gc`, поэтому для точной записи нужна обёртка.

Диагностика не вызывает `ToString`, виртуальный `GetHashCode` или свойства
игровых объектов. Управляемая идентичность получена через `RuntimeHelpers`;
из userdata читается только 4-байтный номер, принадлежащий NLua. Полные скрипты,
команды и адреса игровых объектов специально не записываются. Имена макросов,
пути Lua-файлов и тексты ошибок присутствуют и могут содержать пользовательские данные.

Строковые hooks и синхронная запись увеличивают нагрузку и могут влиять на
воспроизводимость. Скрипт, заменяющий `debug.sethook`, может отключить наблюдение.
Внутренние поля NLua проверены для 1.7.9; при обновлении нужны повторные тесты.
Отключение: `LuaCrashDiagnostics.Enabled = false`, пересборка и перезапуск.

## Проверка и сборка

Пауза Lua- и native-макросов теперь ожидается асинхронно, чтобы не блокировать
игровой framework-поток до нажатия Resume/Stop. Это исправляет зависание при
паузе уже запланированного, но ещё не начавшего исполняться дочернего макроса.
Во время паузы состояние проверяется каждые 25 мс; работающий макрос не получает
дополнительной задержки. Исходный сбой GC, описанный выше, остаётся предметом диагностики.

При выгрузке плагина новые макросы блокируются, активные получают сигнал отмены,
а плагин ожидает завершения их задач перед освобождением сервисов. Завершающие
Lua-функции при выгрузке не запускаются. Уже исполняющийся синхронный Lua-вызов
нельзя прервать принудительно: если он не возвращает управление, выгрузка будет
ждать его завершения.

Из корня репозитория `SomethingNeedDoing`:

```powershell
dotnet run --project tests/LuaCrashDiagnostics
pwsh -NoProfile -ExecutionPolicy Bypass -File tests/MacroPause/Run.ps1
dotnet build SomethingNeedDoing/SomethingNeedDoing.csproj -c Debug -p:UseSharedCompilation=false -p:DebugType=portable -p:DebugSymbols=true
```

Тесты используют настоящий NLua и нативный Lua, без подключения к игре.
Проверяются корутины, очистка и закрытие среды, запись до исходного GetHashCode,
отсутствие дополнительного хеширования/форматирования игровых объектов,
наблюдение SubKinds, отказ журнала, немедленная запись и ротация.

Тест `MacroPause` извлекает исполняемые циклы из обоих движков и компилирует их
вместе с настоящим `MacroPause.cs` в изолированном планировщике framework-потока.
Старый блокирующий wait воспроизводит зависание; исправленные циклы проверяются
на отзывчивость при паузе, Resume/Stop, отмену и сохранение игрового потока для
Lua-вызовов и native-команд. Игра и DLL Dalamud для этого теста не нужны.

Два выражения копирования словарей в `MetadataParser` заменены на эквивалентные
конструкторы `new(dictionary)`: исходный синтаксис `with(...)` не компилируется
установленным .NET SDK 10.0.202. Поведение настроек не менялось.
